# Phase 4.1 hosting options

Reviewed 24 November 2026 for a £0 private staging budget. The staging topology is a static React/Vite web build and an independently deployed Node.js API. Supabase is reserved for later account and database work.

| Option | Free allowance and fit | Restrictions and potential costs |
| --- | --- | --- |
| Cloudflare Pages and Access | Static frontend on Pages. Pages documents free unlimited static asset requests, 500 builds per month, one concurrent build and a 20-minute build limit. Access can restrict preview deployments to approved testers. | Pages Functions use Workers quotas and would require adapting the API. Preview protection must be enabled and verified for every reachable URL, including aliases and the project's production URL. Use the general service terms and acceptable use rules to assess future commercial use. | Vercel Hobby | Suitable technically for a Vite static build. Hobby offers Vercel Authentication for deployment protection and includes 100 GB fast data transfer and 10 GB fast origin transfer per month, plus metered compute. | Hobby is expressly limited to personal, non-commercial use. Skip it for the planned product staging. Running the API as Vercel Functions would change the process and storage model. A later move to Pro entails recurring charges and usage limits. [Hobby limits and terms](https://vercel.com/docs/plans/hobby) · [Pricing](https://vercel.com/pricing) |

## Recommendation

Prefer **Cloudflare Pages with Access for the frontend, and a Render Free standalone API behind verified access controls**, with Supabase Free considered in Phase 4.2. Use synthetic catalogue data initially. This is a candidate for a small staff-only staging group, subject to proof that the frontend and API can both be protected without buying a domain or adding a payment method. A private preview link alone does not protect the public Render hostname. If an Access-protected custom hostname is used, require a domain already under the owner's control and reject bypass requests at the API origin. No domain ownership is assumed. If both services cannot be made private at £0, keep the two-process staging rehearsal on an existing private machine until the owner approves a suitable access arrangement.

## Phase 4.1 execution after approval

1. Review and approve the hosting choice, private tester list, available hostnames and zero-spend controls. Confirm the platform terms still cover the intended private staging use.
2. Choose the two staging origins and an access gate for each. Prove that direct API URLs, preview aliases and unauthorised origins cannot bypass it. Check browser sign-in or cross-origin credential behaviour independently of CORS.
3. Add a configurable public API base URL and exact allowed frontend origin. Keep staging secrets server-side, providers disabled and the built frontend and API on compatible versions.
4. Deploy only behind the verified gates using synthetic data. Test cold starts, recovery, guest and weekly flows, empty vs failed results, desktop, phone and Safari. Record versioned rollback instructions and practise rolling both apps back.
5. Design a durable, shared quota budget, then verify it survives restarts and concurrency before any live provider access. A Render filesystem reset must never reset the effective 450-request limit. Return for approval before enabling live providers, inviting beta users or beginning Supabase account work.
